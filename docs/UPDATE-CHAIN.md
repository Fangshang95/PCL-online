# PClonline 更新链路说明

面向维护者。本文档随公开仓库发布，**不含任何服务器地址、密钥或内部路径**；
真实的自建清单源地址只存在于发布包内的 `update-sources.txt` 与打包机的 secrets 目录。

## 1. 一句话概括

启动器是「引导器 + 应用层」两层：引导器是一个内嵌了完整应用层的单文件 exe，
负责自展开、检查更新、下载与替换，然后拉起真正的主程序；主程序只做「检查并提示」，
运行期不自我修改。更新清单是一份带 **ECDSA 签名**的 `version.json`，
它同时声明了版本号、每个文件的哈希、以及全量安装包的地址与哈希。

## 2. 磁盘上的角色

| 文件 | 作用 | 写入者 |
| --- | --- | --- |
| `PClonline.exe` | 引导器；内嵌应用层 `app.zip` 与清单验签公钥 | 维护者分发 |
| `app\` | 实际运行的程序（当前 102 个文件） | 引导器展开 / 更新 |
| `app\version.json` | **本地版本标记**，仅 `{"version":"..."}` | 引导器每次更新后 |
| `app\update-sources.txt` | 随包下发的清单源列表（一行一个 URL，`#` 开头为注释） | 打包机 |
| `app\.bootstrapped` | 首次展开标记 | 引导器 |
| `app\.update-restart` | 「我已退出干净，请接手完成更新」 | 主程序 |
| `bootstrap.log` | 引导器全程日志 | 引导器 |

> 远端清单与本地版本标记同名 `version.json` 但内容完全不同（远端约 16 KB，本地约 22 B）。
> 排查问题时别看错文件。

## 3. 清单与签名

远端 `version.json` 的结构：

```
version    "v50.11.19"                      ← 版本比较只看它
generated  ISO 时间戳                        ← 客户端不读，供人核对
files      [ {path, size, sha256} × 全部应用层文件 ]   ← 落地前逐文件复核
packages   [ {type:"full", url:"…/releases/download/<version>/app.zip",
              size, sha256} ]                ← 包地址钉死在 tag
```

- 同名的 `version.json.sig`（88 B）是对 `version.json` **原始字节**的 ECDSA P-256 / SHA-256 签名。
- 验签公钥内嵌在引导器与主程序中；**私钥只在打包机上，不进仓库**。更换密钥等同于更换客户端。
- 签名覆盖「版本号 + 每个文件哈希 + 包地址与包哈希」，因此改清单任一字段会验签失败；
  只换包不改清单会被包哈希或逐文件哈希拦下。

## 4. 清单源的解析顺序

引导器与主程序使用同一套规则：

1. 环境变量 `PCL_UPDATE_MANIFEST`（分号分隔；会被子进程继承，两层因此看到同一份）
2. 随包下发的 `update-sources.txt`（`app\` 目录与其上级目录都会查找）
3. **GitHub Releases 兜底源**——恒定追加在列表末尾，无法通过配置移除

设计取向：GitHub 是真相源与最终兜底，自建源只是加速器。配置文件写错、缺失或自建源宕机，
结果都只是回到"稍慢但可用"的老路径，不会让玩家彻底收不到更新。

两个入口用不同的 URL 语义，是有意为之：

- **清单入口跟 `latest`**：回答"最新版是谁"本来就该随最新发布漂移。
- **包地址钉在 tag**：清单自报版本是 X，包就必须永远是 X 的那一份，不能各说各话。
  若包地址也写成 `latest/download/app.zip`，一旦清单比线上 `latest` 跑得靠前
  （例如先把新清单发到自建源、GitHub 还没发布），玩家按清单升到新版却拿回旧包，
  哈希不符、更新静默失败，且现场极难定位。

**明文 HTTP 源的额外约束**：以 `http://` 开头的源**必须取到签名并验签通过**才采信；
`https://` 源沿用过渡期策略（取到签名必须验过，取不到只记录告警）。

## 5. 版本判定规则

安装地板取 `max(本地应用层版本, exe 内嵌版本)`。

| 清单版本 vs 地板 | 行为 |
| --- | --- |
| 高于 | 更新（引导器安装；主程序提示"发现新版本"） |
| 相等 | "已是最新版本"，不动任何文件 |
| 低于 | **弃用该源，继续试下一个**，对 GitHub 兜底源同样生效 |
| 版本号无法解析 | 放行（护栏的失效方向是"不拦"，避免误伤正常更新） |

地板取两者最大值的原因：本项目的主要分发方式是"把一个 exe 转发给好友"，玩家会直接把它
覆盖进旧目录；那一瞬间 `app\` 里还是旧版，只看本地会把刚发来的新版误判成降级。

**为什么禁止降级**：完整性校验（验签 + 包哈希 + 逐文件哈希）只能证明"这份清单是真的"，
证明不了"它是最新的"。一份签名有效、包哈希自洽的**陈旧**清单会一路通过所有旧防线，
把玩家的应用层整体覆盖回旧版本——这是内容寻址与签名体系的固有盲区，必须由方向性规则补。
本项目对坏版本的处理方式从来是"作废 + 往前发一个更高的版本号"，而不是把玩家退回旧版，
因此不需要、也不应该保留任何自动降级路径。

## 6. 冷启动时引导器做什么

1. 内嵌版本与 `app\version.json` 不一致 → 清理并重新释放应用层（无可用运行时的场景除外，
   此时保留旧版并提示安装运行环境，避免把玩家原有的可用版本删掉）
2. 按上面的顺序解析清单源，逐个尝试：清单 8 秒上限、签名 4 秒上限、**全局 15 秒预算**
   —— 取清单不吃更新包那个长超时，保证双击 exe 不会因为源不可达而长时间看不到界面
3. 验签 → 禁降级判定 → 得到清单
4. 版本不同则下载 `app.zip`（绝对 GitHub 地址，长超时）→ 校验包 sha256
   → 解压 → **逐文件 sha256 复核** → 全部通过才覆盖 `app\` 并写版本标记
5. 任何一步失败都放弃本次更新、**不阻断启动**，且不会落地"半个更新"
6. 拉起 `app\PClonine.exe`，数据目录固定在启动器根目录（`PCL_DATA_DIR`），
   并等待其退出；若退出时留有 `.update-restart`，则删除标记后回到第 2 步重跑
   —— 此时文件锁已全部释放，替换才可能成功

运行环境（.NET Desktop Runtime 10）由玩家自行从微软官网安装：启动器只检测并给出链接，
**不联网下载、不提权安装、不写任何系统目录**。

## 7. 主程序内的检查

| 机制 | 参数 |
| --- | --- |
| 启动后台预热 | 挂在既有启动加载器池上；缓存不足 5 分钟时完全不联网 |
| 页面首屏 | 30 分钟内直接显示上次检查结果，不再空等网络 |
| 静默刷新 | 缓存超过 5 分钟才刷新；刷新期间保留原文案与「退出并更新」按钮 |
| 时间预算 | 全局 10 秒；单源 8 秒且每源只尝试 1 次（旧实现是 30 秒 × 3 次串行重试） |
| 结果收口 | 全部源失败 → 回退到缓存；仍无缓存才提示"暂时获取不到更新清单（不影响使用）" |

检查结果缓存在机器全局临时目录（不随数据目录走），同一台电脑上多个目录共用一份。
缓存文件按无 BOM 写出以保持与签名原文一致，时间戳用 Unix 秒——若按本地时区解释，
东八区会把缓存算到 8 小时之后，导致永远"还新鲜"、玩家再也等不到新版本。

## 8. 故障时玩家分别看到什么

| 故障 | 行为 |
| --- | --- |
| 自建源宕机 / 404 | 极快跳过，转 GitHub，玩家无感 |
| GitHub 不可达 | 自建源正常返回，检查仍在亚秒级完成 |
| 两者都不通 | 提示稍后再试；游戏与联机不受影响 |
| 包下不动 / 校验失败 | 放弃更新、不落地半个包，下次启动自动重试；照常启动 |
| 清单被篡改 | 验签失败弃用该源；只换包则被包哈希或逐文件哈希拦下 |
| 清单"合法但更旧"（镜像残留、重放） | 被禁降级规则弃用 |
| 缺 .NET 运行环境 | 弹窗给出官方下载链接 |

## 9. 发布流程（顺序不能颠倒）

```
1) 打包与签名        python build_update.py <新版本>
2) 提交并推送         commit → push origin main     ← tag 必须有对应提交
3) 发布 GitHub Release publish_github_release.py --tag <新版本> --dir <发布目录>
                     ← 建 Release 会同时在该提交上创建 tag，latest 随之切换
4) 发布自建清单源      publish_server_update.py --dir <发布目录>   （可选，只传清单与签名）
```

第 2、3 步必须在第 4 步之前：包地址钉在 tag，tag 与 Release 不存在时清单会指向 404。

## 10. 自检：线上是否自洽

```
取 latest 的 version.json → 用打包签名工具以公钥验签
→ 取清单里的包地址（跟随重定向）确认 HTTP 200 且 content-length 等于清单声明的 size
→ 比对远端资产与本地产物的 sha256
```

## 11. 紧急处置

- **停用自建清单源**：删除服务器更新目录里的 `version.json` 与 `version.json.sig`。
  客户端会自动回落 GitHub，无需发版、无需重启任何服务。
- **目录请保留为空目录**：更新闸门在目录不存在时会直接返回 503，留着空目录行为更干净。
- **坏版本**：往前发一个更高版本号的修复包；不要试图把玩家退回旧版。

## 12. 已知缺口

- 自建源的"闲时供货"闸门目前同时约束清单与包体。清单只有十几 KB，
  而闸门是按大包设计的——在线人数高时快源会整体失效、退回兜底源。待改为只约束资产分支。
- 引导器仍在拉起主程序之前完成取清单（已有 15 秒上限），完全异步化是更大的改动。
- 分发用的启动器 exe 与 `app\` 里"不要双击"的那个文件同名（体积分辨：本体约 27 MB，
  应用层约 0.4 MB）。根治需要统一命名。
